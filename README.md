## Зачем это всё?

Когда я работала с заказчиками на фрилансе, я часто сталкивалась с тем, что у них были разрозненные сервисы, ручные деплои и полное отсутствие мониторинга. Я захотела собрать **референсную архитектуру**, которая:

- легко масштабируется,
- сама себя восстанавливает после сбоев,
- даёт полную картину происходящего через метрики, логи и трейсы,
- управляется через Git (никаких ручных изменений в кластере).

Этот проект — результат моего опыта и подхода к SRE. Весь код и манифесты открыты, чтобы вы могли оценить мой стиль работы.

---

## Архитектура

Мы строим систему бронирования билетов. В ней четыре микросервиса:

- **API Gateway** (Ingress) — точка входа для всех запросов.
- **Booking Service** — создаёт брони, сохраняет их в PostgreSQL, отправляет события в очередь.
- **Notification Service** — слушает очередь RabbitMQ и эмулирует отправку уведомлений.
- **Вспомогательные сервисы** — PostgreSQL, Redis, RabbitMQ.

Обмен между сервисами — **асинхронный** через очередь, чтобы Booking Service не ждал, пока письмо уйдёт.

## Как запустить у себя

### Локальный запуск (для разработки)

Всё поднимается одной командой через Docker Compose:

```bash
git clone https://github.com/Alimerize/ticket-booking-platform.git
cd ticket-booking-platform
docker-compose up --build
```

После запуска:
- Booking API будет доступен по адресу: [http://localhost:8000/docs](http://localhost:8000/docs)
- RabbitMQ Management: [http://localhost:15672](http://localhost:15672) (guest/guest)

### Запуск в Kubernetes (продакшн)

1. Установите minikube или kind.
2. Включите ingress-контроллер.
3. Соберите образы внутри окружения кластера:
   ```bash
   eval $(minikube docker-env)
   docker build -t booking-service:latest ./booking-service
   docker build -t notification-service:latest ./notification-service
   ```
4. Примените манифесты:
   ```bash
   kubectl apply -f k8s/
   ```
5. Добавьте локальный DNS (для minikube):
   ```bash
   echo "$(minikube ip) booking.local" | sudo tee -a /etc/hosts
   ```
6. Откройте браузер: [http://booking.local/docs](http://booking.local/docs)

## Мониторинг и наблюдаемость

Я считаю, что SRE — это не про "починить, если упало", а про "увидеть, что упадёт, за час до этого". Поэтому в проекте настроен **полный стек наблюдаемости**:

- **Prometheus** — сбор метрик (время ответа, количество ошибок, загрузка CPU).
- **Grafana** — дашборды с золотыми сигналами (Latency, Traffic, Errors, Saturation).
- **Loki** — централизованный сбор логов.
- **Tempo** — распределённая трассировка запросов.

Установка через Helm (описана в отдельном документе `observability.md`).

## GitOps: управление через ArgoCD

Всё, что происходит в кластере, должно быть описано в Git. Это единственный источник истины.

1. В кластере установлен ArgoCD.
2. Он синхронизирует состояние с этим репозиторием.
3. Любое изменение манифестов → автоматический деплой.

Такой подход исключает «слепые» правки на продакшене и даёт уверенность в воспроизводимости.

## Мои мысли (почему именно так)

- **Асинхронность** через очередь — чтобы не тормозить основной сценарий бронирования.
- **PostgreSQL** — потому что ACID важна для финансовых операций.
- **Redis** — для быстрого кэша событий (можно расширить).
- **Kubernetes** — даёт возможность легко масштабировать и управлять отказами.
- **GitOps** —  я устала от ручных деплоев и хочу, чтобы всё было автоматизировано.
